# Next.js 16 — deltas that affect this project

The assessment proposed Next.js 15. We start on **16.3.4** instead: `npm audit`
reported a high-severity postcss advisory reachable through Next 15, fixed in
16, and this is a greenfield project with no migration cost.

Next 16 ships `AGENTS.md` (and `CLAUDE.md` → `@AGENTS.md`) into the repo root,
regenerated by `next dev`, warning that its APIs differ from most training data.
Docs are bundled at `node_modules/next/dist/docs/`. **Read them before writing
framework code** rather than relying on recall. Items below are the ones that
bite this codebase specifically.

## Applied already

| Change | Effect here |
|---|---|
| Node 20.9+ minimum (18 dropped) | `engines.node` set to `>=20.9.0` |
| `next lint` removed; `next build` no longer lints | `lint` script deleted. Add Biome or ESLint directly if we want linting |
| Turbopack is the default bundler | No action — build is clean |

## Pending — phases 4, 5 and 9

**Async request APIs.** `cookies()`, `headers()`, `draftMode()`, and `params` /
`searchParams` are async-only; Next 15's synchronous compatibility shim is gone.
Every auth helper and route handler must await them:

```ts
const cookieStore = await cookies();          // not cookies()
export async function GET(req: Request, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;                 // not params.id
}
```

This touches `withRole()`, every `/api/*/[id]` handler, and session reads.

**`middleware.ts` → `proxy.ts`.** The file and its named export are renamed, and
`proxy` runs on the **Node.js runtime only** — the edge runtime is not
supported there. This matters if Phase 4 puts auth checks in middleware. Given
RBAC must be enforced per-route anyway (§8), the plan stays: enforce in
`withRole()` inside each handler, and use `proxy.ts` only for coarse redirects
(unauthenticated → login), never as the authorization boundary.

**Caching.** `revalidateTag` / `updateTag` / `refresh` semantics changed and PPR
is available. The timetable is realtime and per-user, so most of it must stay
uncached — verify no route accidentally inherits static caching in Phase 5.

## Watch during Phase 9 (SSE)

`proxy` being Node-runtime-only is helpful: the SSE route handler wants the
Node.js runtime for MongoDB change streams regardless. Confirm the streaming
route is not statically optimised and that `X-Accel-Buffering: no` (already set
in `next.config.ts`) survives to the client.
